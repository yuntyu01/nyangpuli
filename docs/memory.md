# 개인 기억: 실제 구현 범위와 비교 방법

현재 기본값은 **사용자가 확인한 사실을 직접 저장하는 Go 파일 저장소**다. 출처 사건 ID와 사건 시각을 함께 저장하며, 정정·늦게 도착한 과거 사건·사용자 분리·삭제를 처리한다. 선택적으로 **Mem0 OSS REST 서버**를 붙일 수 있다. Mem0에 접속하거나 LLM을 호출하지 않아도 로컬 테스트가 실행된다. 두 방식의 한국어 추출 품질이나 상담 효과가 더 좋다고 검증한 것은 아니다.

## 1. 기본 저장소

`internal/memory.Store`는 외부 Go 의존성이 없는 단일 프로세스 JSON 저장소다. 빈 경로로 열면 메모리에서만 동작한다. 파일 모드는 같은 디렉터리에 임시 파일을 쓰고 `fsync → rename`한 후 메모리 상태를 바꾼다. 파일은 `0600`, 새 디렉터리는 `0700`으로 만든다. 쓰기 실패는 현재 메모리 상태도 바꾸지 않는다.

```go
store, err := memory.Open("data/private/memory.json")
if err != nil { return err }
_, err = store.Set(authenticatedUserID, memory.Fact{
    Key:           "relationship_status",
    Value:         "헤어짐",
    SourceEventID: "message-20261003-001",
    ObservedAt:    time.Date(2026, 10, 3, 10, 0, 0, 0, time.UTC),
    Note:          "사용자가 직접 확인한 현재 상태",
})
```

| 필드 | 의미 |
|---|---|
| `key` | 같은 사실을 갱신하기 위한 고정 키. 예: `relationship_status`, `contact_boundary` |
| `value` | 사용자가 확인한 내용. 추측·성격 추론을 자동으로 넣지 않음 |
| `source_event_id` | 확인한 원래 메시지나 사건의 ID. 실제 원문 보관과 권한 확인은 호출 앱 책임 |
| `observed_at` | 사실이 적용된 사건 시각. 업로드 시각과 구분하며 RFC3339로 전달 |
| `recorded_at` | 저장 시각. 서버가 생성 |
| `supersedes` | 새 현재 사실을 저장할 때 대체한 이전 현재 기록의 ID |
| `current` | 현재 같은 키에서 가장 최신인 기록인지. 조회 시 저장 상태에 맞게 계산 |

`Set(userID, fact)`는 기록을 추가한다. 같은 사용자·키·원본 사건의 동일 입력은 같은 ID를 반환한다. 같은 사건을 다른 값으로 다시 쓰거나, 같은 사건 시각에 다른 값을 넣으면 `ErrConflict`로 거부한다. **정정은 새 사건 ID와 실제 정정 시각으로 기록**한다. 늦게 들어온 과거 사건은 이력에 남지만 최신 값을 되돌리지 않는다. `supersedes`는 삽입 시 대체 관계이며, 늦게 추가한 과거 사건 때문에 이전 기록을 소급 수정하지 않는다.

`Current(userID)`는 키별 최신 사실, `History(userID, key)`는 시간순 이력, `DeleteUser(userID)`는 해당 사용자의 현재 사실과 이력을 삭제한다. 다른 사용자 자료에는 영향을 주지 않는다. 사용자 ID는 요청 JSON이 아니라 서버에서 인증한 사용자 정보로 전달해야 한다.

**운영 범위:** 실험용 단일 프로세스에 적합하다. 파일은 평문이며 암호화·프로세스 간 잠금·백업 삭제·보존 기간·동의 관리가 없다. 여러 인스턴스가 같은 파일을 쓰면 안 된다. 실제 서비스에서는 트랜잭션 DB와 사용자별 접근 통제, 삭제·보존 정책을 붙여야 한다. 이 저장소의 삭제가 별도 Mem0 서버나 앱 로그까지 지우지는 않는다.

## 2. 선택적 Mem0 연결

검토한 계약은 [Mem0 OSS `server/main.py`](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/server/main.py)의 커밋 `26cdefb46600c0fa5953c4b5ee5003c125539fc4`다. 직접 작성한 Go 어댑터이며 Mem0 Python 구현을 이식한 것은 아니다. **호스팅 플랫폼의 `/v1` API와 다르다.**

| 메서드 | 실제 OSS 요청 | 앱에서 추가한 제한 |
|---|---|---|
| `Add` | `POST /memories` | 서버의 `user_id`, 메시지, 명시적 `infer`만 전달 |
| `Search` | `POST /search` | `filters.user_id` 강제, 결과 소유자가 다르면 전체 거부 |
| `Get` | `GET /memories/{id}` | 결과 `user_id` 확인 |
| `Update` | `PUT /memories/{id}` | 먼저 `Get`으로 소유자 확인, 텍스트만 갱신 |
| `Delete` | `DELETE /memories/{id}` | 먼저 `Get`으로 소유자 확인 |
| `DeleteUser` | `DELETE /memories?user_id=...` | 항상 사용자 범위 지정. upstream 관리자 권한 필요 |

```go
remote, err := memory.NewMem0(os.Getenv("MEM0_URL"), os.Getenv("MEM0_API_KEY"), nil)
if err != nil { return err }
found, err := remote.Search(ctx, authenticatedUserID, "최근 연락에 관한 합의", 5)
```

API 키는 `X-API-Key` 헤더로만 전달한다. 외부 서버는 HTTPS, 로컬 테스트는 loopback HTTP를 허용한다. 리디렉션을 따라가지 않으며, 오류 응답의 본문을 사용자에게 전달하지 않는다. 어댑터는 확인한 사용자 ID를 반드시 요구하지만 **앱 로그인이나 세션 인증 자체를 구현하지 않는다**.

`infer=false`는 선택한 메시지를 그대로 저장한다. `infer=true`는 Mem0가 설정한 LLM에 사실 추출을 요청하므로 비용과 외부 전송이 발생할 수 있다. 테스트는 외부 모델을 호출하지 않는다. 검토한 Mem0 소스의 기본 추출 경로는 추가형이며, 모순된 모든 과거 사실을 자동으로 정정한다는 보장이 없다. 명시적 관계 상태·상대의 연락 거절 등은 로컬 현재 상태로 관리하고, 검색 결과의 시점·출처를 확인하는 방식부터 비교하는 것이 좋다. 검색 자료는 사용자 데이터이며 시스템 명령으로 취급하면 안 된다.

## 3. 재현 가능한 구현 시험

```sh
go test -race ./internal/memory
```

현재 테스트는 다음 동작을 확인한다. 전부 합성 입력 또는 `httptest` 로컬 서버를 쓰며 실제 사람의 대화나 실제 Mem0 배포는 사용하지 않는다.

1. `연애 중 → 헤어짐` 이후 과거 `갈등 후 대화 중` 사건을 늦게 저장해도 현재가 `헤어짐`으로 유지되는지.
2. 같은 사건 ID를 두 사용자가 써도 분리되고, 파일 재시작과 한 사용자 삭제 후에도 분리되는지.
3. 재전송은 중복 저장하지 않고 사건 ID·시각 충돌은 거부하는지.
4. 디스크 쓰기 실패 때 메모리 상태를 잘못 바꾸지 않는지.
5. 깨진 저장 파일과 출처·시각이 없는 사실을 거부하는지.
6. 동시에 다른 사용자의 사실을 써도 누락되지 않는지.
7. Mem0 HTTP 경로·요청 필드·헤더·소유자 확인이 검토한 OSS 계약과 맞는지.
8. 다른 사용자 결과·수정·삭제, 리디렉션 키 전송, 민감한 오류 본문 노출을 막는지.

**이 시험의 결론은 구현 동작에 한정된다.** 한국어 추출 정확도와 상담 품질은 별도다. 다음 실험에서는 같은 대화를 기억 없음 / 확인한 사실 저장 / Mem0 추출·검색 조건에 넣고, 정정 실패·지난 사실을 현재로 사용·근거 없는 사실 생성·사용자 혼입을 따로 세어야 한다. Mem0 실서버 테스트를 실행하기 전에는 HTTP 계약 시험 통과를 실제 연동 성공이라고 기록하면 안 된다.

## PostgreSQL 개인 기억 정정과 삭제

인증된 사용자는 `PUT /v1/memory/{id}`로 기존 `key`, `source_event_id`, `observed_at`, `value`, 선택 `note`를 포함해 정정할 수 있다. 사건 ID와 키는 유지해야 한다. `GET /v1/memory/{id}/revisions`는 정정 전 이력을 반환하며 `DELETE /v1/memory/{id}`는 해당 기억과 정정 이력을 지운다. 모두 서버 인증의 계정 범위에서 처리한다. 이 API는 PostgreSQL 모드에서 지원되며 기존 JSON 모드에서는 503이다.

최신 기억을 삭제하면 과거 동일 키의 기억을 자동으로 현재값으로 되돌리지 않는다. 지연 도착한 과거 사건이 현재값으로 되살아나지 않도록 계정·기억 키·삭제 시각만 포함한 마커를 둔다. 삭제한 값과 사건 ID는 마커에 저장하지 않으며 계정 삭제 시 마커도 삭제한다. 마커 이전 사건은 저장되더라도 검색 가능한 현재 기억으로 등록되지 않는다.

기억 추가·정정·삭제 시 메모리를 사용했던 PostgreSQL 생성 작업은 일괄 무효화하고 해당 근거와 결과를 지운다. 세대 확인으로 기억 조회 후 작업 등록 사이의 변경과 실행 중 작업의 결과 재저장을 막는다. 이전 상담 자료에서 기억 사용 여부를 구분할 수 없는 레거시 작업은 보수적으로 무효화한다. 메모리를 사용하지 않은 신규 작업과 다른 계정의 작업은 유지한다. 무효화된 작업 키는 중복 유료 호출을 막기 위해 남고 상태 조회에서 `invalidated`로 표시된다. 연결된 구매 기록은 그대로 유지되며, 결과 복구·환불·재발급 정책과 실제 스토어 연동은 아직 구현되지 않았다. 이미 사용자에게 전달됐거나 외부 모델 공급자에게 전송된 내용은 회수할 수 없다. 백업, 별도 외부 서비스 및 JSON 저장소의 기존 풀이 스냅샷 삭제는 이 PostgreSQL 작업에서 처리하지 않는다.

## 대화에서 나온 기억 (2026-10-30)

PostgreSQL 모드의 연속 상담은 사용자 메시지에서 기억 후보를 저장한다. 기억은 `fact`(최신 정정 우선)와 `episode`(시점·대상·상황별 보존)로 나뉘고, 출처가 사용자 확인(`user_confirmed`), 메시지 인용(`user_stated`), AI 추정(`ai_inference`, 미확정)으로 구분된다. AI 추정은 생성 문맥에 쓰이지 않는다. 자세한 규칙은 [연속 상담과 개인 기억](conversations.md)에 있다.
